## How to read this

This case study is written for two readers. A person can read it top to bottom. An agent can follow the section **The method as a checklist**, which is written as steps to carry out. Every prompt below is quoted exactly as I typed it, typos included, because the point is that they were short and ordinary. Only a local folder path is shortened, in square brackets. What made them work is what sat underneath them.

## The loop

<Diagram name="promptLoop" caption="The loop. A review below the bar sends the work back to Change; nothing goes live before my approval." />

1. **Rules first.** A project file states the design lock, the quality bars and the evidence rule, and names the design system as the single source of truth for the design language. The agent reads it before every task.
2. **One-line request** with a role, a scope and, when it matters, a bar ("rate your work... if below 9...").
3. **Measure.** The agent finds the cause and puts a number on it before changing anything.
4. **Change** on a branch, inside the design lock.
5. **Gate.** Every route, ten sizes, both themes, accessibility, contrast, overflow, states, performance, mobile. It must end with PASSED.
6. **Independent review.** A fresh reviewer scores it from screenshots and the built site. Below the bar, fix what they found and ask a new reviewer.
7. **Record.** One audit row per change of look, one verification section per phase, with evidence.
8. **Approve.** I read the report and say yes; only then does it go live.

## The prompt patterns that did the work

### 1. Cast a role and name the whole scope

```text
you are an interaction designer and UI developer, i need you to review all the front end pages and improve the animation you can use any animation library lke GSAP or something i just want a good animated front end with proper flow without effecting overall layout and experience
```

```text
you are an Senior Graphic Designer, I need you to review all the pages and improve the iconography, create illustrations where ever seem fit there should not be deadspace where if there is a Heading and paragraph on the left then should should always be an respective illustration of selected work. and in selected work swip the preview images are not showing properly
```

**What happened.** The role changed what the agent looked for. As an interaction designer it inventoried every moving thing on the site and gave each block one owner, so two scripts never animated the same heading. As a graphic designer it wrote a survey script that finds every heading and paragraph with an empty band beside it, then drew a picture for each one it found in the site's own drawing style.

**Why it works.** "All the pages" plus a role turns a vague wish into an audit with a list at the end. The constraint I added in passing ("without effecting overall layout") became a measured rule: motion may not cost a page its layout-shift budget.

### 2. Set the bar as a number, and make it loop

```text
check your work and give yourself rating on a sccale of 1-10, if below 8 rating resolve it and get higher rating
```

```text
rate your work on a scale of 1-10 rating, if rating is below 9 try your best to improve to 10/10
```

**What happened.** The agent did not grade itself. It gave screenshots and the built site to a fresh reviewer, recorded the score, fixed what the reviewer named and asked again. The admin dashboard went 6, 7.5, 8. Home's design process section went 7, 8.5, 9. Buttons and calls to action went 7, 7, 8. The illustrations work went 7, then down to 6.5 when the reviewer judged my second pass, and that drop is what pointed at the swipe-deck pictures still being too small.

**Why it works.** A number gives the loop a stopping point. A different reviewer keeps the number honest.

### 3. Name the symptom, not the fix

```text
why animations are not working
```

```text
the animations are still not working, figure out why
```

**What happened.** The site's motion was fine. My PC had Windows' Animation effects turned off, so the browser reported reduced motion and the site, correctly, stood still. The agent proved it by reading the setting and the browser's media query, and by running the site in a browser with motion allowed. Its first decision was to keep respecting the setting.

**Why it works.** If I had written "add GSAP scroll triggers", I would have got more animation that still did not run on my laptop.

### 4. Correct the reading in one sentence

```text
i think you did not understand, I want on-scroll animation revealing effect on front end page, the motion should be smooth and organized
```

**What happened.** I did not want a still page on my own laptop. This sentence changed the decision: under reduced motion the site now keeps every scroll reveal and the first view as a fade, opacity only, with nothing moving. Visitors who asked for less movement still get none, and nobody gets a page that never comes alive. The rule went into the project file, and the checks now test both modes.

### 5. Turn a one-time complaint into a permanent check

```text
add one more quality check, all the image that are uploaded should be properly viewed in viewcards, thumbnails without getting cropped both in desktop and mobile. 

also create image preview feature, so that when user clicks on images the popup should open showing full image with zoom in and zoom out options
```

**What happened.** The gate gained an image-crop check that fails any picture drawn with cropping into a box of another shape, and every card now shows the whole picture over a blurred copy of itself. The preview opens any page picture full size with zoom steps, and has its own behaviour test.

My own audit prompts, which I use on every design system I make, end the same way:

```text
I need you to think hard and do a heuristic analysis of this entire project. Make sure there are no design issues, Spacing issues, no text overflow issues, no visual inconsistencies, No contrast ratio issues, no dark mode and light mode switching issues, No WCAG guidelines rule breaking. No a11y accessibility rule breaking (make a rule in this project, so that if we create new pages this rule should apply alltimes without any issues or text overflow)
```

**Why it works.** "Make a rule in this project" is the most valuable phrase in the set. A fix repairs one page; a rule protects every page that comes after it.

### 6. Delegate the reversible decisions

```text
you decide, dont put anything on me
```

```text
yeah go with A. Command centre
Recommended
```

**What happened.** I wrote "you decide" ten times in three weeks. Each time the agent chose, wrote the choice and its reason into the audit log, and kept going. When a choice was big enough, it offered options with one marked as recommended, and I picked in four words. Irreversible actions (publishing, accounts, anything costing money) were never inside "you decide".

### 7. Bring your own material

```text
i have created a logo for this project can you properly incorporate it you can find it here [the brand kit folder]
```

```text
i need you to incorporate this google hr formula 

Accomplished [X] as measured by [Y] by doing [Z]
```

```text
on highlevel what now a i am doing usually is i get the breifing about design then i go create logo/design language then create a design system in claude design make it perfect and make it follow top 10 UX laws and design principles then i create templates in it for tech and non tech users.
```

**What happened.** The logo was drawn from the brand kit's own outlines, never retyped in a font. Every career line was rewritten in the XYZ form, from facts already on the site. My description of how I work became the design process section on Home, and a reviewer was asked specifically to remove any step I had not described, which it did (research and testing with people, which I had not claimed).

**Why it works.** The agent cannot invent what it does not know, and the evidence rule forbids it from trying. Real material is what lets it finish.

### 8. Observe like a user

```text
designer feedback:
when i share the link i am not getting fevicon or thumbnail can you resolve it
```

```text
i think Beyond the canvas
section we can remove this does not make sense also can you create some illustration in Human + Agent section right hand side looks empty we can show illustration there
```

**What happened.** Each observation was reproduced, measured and fixed at its cause. One sentence from a real moment of use carried more information than a page of specification.

### 9. Keep check-ins short and let the records carry the detail

```text
status?
```

I sent 89 check-ins like this one. Each answer gave what was running, what had passed with its numbers, what was next and how long it would take. When I needed the laptop back:

```text
can you pause everything right now, i  need to put PC on sleep later we will continue
```

The agent stopped every process it had started, saved the work as a commit on the branch, and wrote down where to resume. My next prompt was one word, `continue`.

### 10. Make one source of truth for the design language

```text
while we are on it i have made few improvements to design system can you incorporate them into our portfolio it could be anything i let you decide
```

```text
the design system is ready incorporate it also made changes to logo system also change the logo of this project properly
```

And, written as the rule this case study ends on:

```text
make a rule  to use a single source of truth for design language example Aleem Design System Artificats Link
```

**What happened.** My design language lives in one place, the Aleem Design System I build in Claude Design and share as an artifact. The site does not keep a second opinion of it: its colours, type, spacing, radii and motion are tokens in one file, and the project's rules say so (one source of truth for tokens, a new token only with my approval). When I improved the system, the agent read the artifact, compared it with the site's tokens and carried the changes across one by one, each with a measured reason. Two examples: the strong edge on dark panels went from 0.28 to 0.36 opacity, which raised its contrast from 2.50 to 3.28:1, and the darkest action blue moved a step so white labels on it went from 6.87 to 7.09:1. What the site's own rules had already improved went back the other way, as a note for the system. The logo came from the kit's own drawings, never retyped in a font.

**Why it works.** With one source, "make it on brand" stops being a matter of taste. Every page, prompt and reviewer checks against the same file, and a change made once in the system reaches every screen.

**How to write it.** Name the source and its authority in the rules file, for example: use [the Aleem Design System artifact link] as the single source of truth for the design language; take colours, type, spacing, radii, shadows, icons and motion only from it; when it changes, carry each change into the tokens and record it; if a page needs something the system lacks, propose an addition to the system rather than a one-off value. On a public page the link appears only once the artifact is shared and holds nothing private, which is why it is in square brackets here.

## The guardrails that made short prompts safe

- **One source of truth.** The design language comes from the design system and nowhere else.
- **Design lock.** Existing tokens and components only. A change of look is either a defect fix with its rule, or a proposal waiting for my approval.
- **Evidence rule.** No "done", "fixed" or "perfect" without a measured value, a passing check or a screenshot path.
- **Never invent.** Unknown facts stay as marked placeholders, and the gate fails a built page that still shows one.
- **Never weaken a check.** Fix the cause, or ask.
- **Branch, gate, review, approve.** Nothing reaches the live site without all four.

## A prompt template you can copy

```text
You are a [role: senior product designer / interaction designer / QA engineer / graphic designer].
Review [scope: every page / every admin page / every card component] of this project.
Goal: [one sentence about what should be true when you are done].
Read the project's rules file first and keep to it: design lock, accessibility, overflow, states, performance.
Use [my design system link] as the single source of truth for the design language: colours, type, spacing, radii, icons and motion come only from it.
Measure before you change anything, and fix causes, not symptoms.
If a problem could come back, add a check for it so it cannot (make it a rule in this project).
Run the full quality checks; do not weaken any check to make it pass.
Then have a fresh reviewer who did not do the work rate it 1 to 10 from screenshots and the built site.
If it is below [8 / 9], fix what the reviewer found and ask a new reviewer. Stop at [the bar].
Report what changed, the evidence for each claim, the ratings, and what needs my decision.
Do not publish until I say yes.
```

## The method as a checklist

For an agent improving the UI and UX of an application on a designer's behalf:

1. Read the project's rules file and audit log before acting. If there is no rules file, propose one: design lock, accessibility bar, overflow rules, states, performance budgets, evidence rule.
2. Find the design system the owner names as the single source of truth for the design language, and take every colour, type size, space, radius, icon and motion value from it. If the project's tokens differ from it, report the differences; never add a one-off value.
3. Restate the request as a role, a scope and a measurable goal.
4. For each finding, measure it (a ratio, a width, a count, a share) and find its cause in the code before changing anything.
5. Change only inside the design lock. A change of look that is not a defect fix is a proposal for the owner.
6. When a complaint could recur, add an automated check for it to the project's quality run.
7. Run the project's quality checks on every route, width and theme the change touches. Never weaken a check.
8. Get a score from a fresh reviewer that did not do the work, given screenshots and the built site. Verify each finding before acting on it. Repeat with a new reviewer until the bar in the prompt is met, and record every score, including the ones that go down.
9. Record each change of look with its reason, and each phase with its evidence.
10. When told "you decide", decide the reversible things, record the decision and its reason, and keep going. Never decide publishing, accounts, payments or anything about other people.
11. Report with evidence, then wait for the owner's approval before anything goes live.

## What did not work

- **Self-rating.** My first "rate your work" answers were generous. Independent reviewers were stricter, and their scores are the ones in this case study.
- **Long runs on a laptop.** A full gate took hours and slowed the machine ("my system keep getting hanged while these running"). Splitting the checks into lanes on the changed routes, at low priority, made it usable.
- **Waiting.** Most of my 89 check-ins were waiting on those runs. Smaller phases would have meant fewer of them.
- **Temporary files.** A cleanup of the temporary folder deleted helper scripts mid-task. Committing the work to the branch early is what protected it.
